# 阶段 2 认证与用户设计

2026-09-14，温晓确定的本轮实施设计。保留 Cookie、账号、密码和管理员二次验证体验；最终认证重设计仍单独安排。

## 会话边界

采用 `cookie 0.18.2` 解析及生成 Cookie，`uuid 1.26.1` 的安全随机 UUID v4 生成不透明标识，Fred 访问独立命名空间的 Redis。标识使用两个 UUID v4 的连续十六进制文本，Redis key 使用标识的 SHA-256。Cookie 不承载身份、角色或签名声明。

原计划的 tower-sessions 是候选。本轮检查了 0.15.0 的 SessionStore 与中间件源码：通用记录保存位于响应后，默认整份覆盖，不直接提供本项目所需的字段级原子条件更新。与其组合旧 Redis 适配器再扩展通用记录协议，本轮采用范围有限的类型化 Redis 会话模块，仅提供创建、读取续期、删除、二次验证及当前会话版本推进五类操作。密码、Cookie 解析、随机数和摘要继续使用现成库，不自行实现密码算法。

- Redis 哈希仅存 userId、sessionVersion、观测角色和二次验证时间；TTL 默认 30 天。普通请求读取并只更新 TTL，不保存整份身份对象、不轮换标识。
- 登录和注册创建新标识；替换已有会话时，在同一 Lua 操作中建立新记录并删除旧记录。碰撞必须重试，不能覆盖现有记录。
- 退出删除记录。其余更新一律要求 key 仍存在且 userId、sessionVersion、观测角色与预期一致。更新不能隐式创建 key，因此旧请求不能恢复已退出的会话。
- 二次验证与密码变更采用原子字段更新。改密推进 PG sessionVersion 并清除当前会话的二次验证；正在进行的旧版本验证不能写回新会话。
- 改密在哈希计算后、写 PG 前，先按当前身份在 Redis 建立带随机 nonce 的 60 秒转换标记；已有转换拒绝重复开始。PG 提交后按同一 nonce 推进版本并清除二次验证和标记；明确的版本冲突清除标记，不确定结果保留至期限。任何更新都不复活已经退出的会话。
- 普通请求遇到 PG/Redis 版本暂时失配且转换标记有效时，有限重读后返回 503，不能误删或返回 401 使客户端退出。失效删除在 Lua 内再核对身份及没有有效转换标记，保护检查与删除之间的竞争；其它旧设备没有该标记，仍正常失效。
- 每次需要身份时从 PG 加载当前账号，检查 deleted、sessionVersion 和当前 role。会话中的角色不授予权限。观测到角色变化就原子清除二次验证状态。
- Redis 不可用时，受保护操作返回 503。公开列表不要求会话；带会话访问依赖身份的私有资源时，依赖故障不能降级为授权放行。
- Cookie 默认 `LYCORIS_SESSION`、路径 `/`、HttpOnly、SameSite=Lax、30 天；Secure 和 Domain 可配置。并行验收必须覆盖独立 Cookie 名，避免与 Java 混用。正式切换时需要重新登录的安排属于阶段 4。

## 密码与权限

BCrypt 沿用 Java 默认工作因子 10，明确验证 $2a/$2b/$2y、UTF-8 和 72 字节边界。历史明文仅在存储值不具有 BCrypt 或 `{...}` 编码前缀时允许比较，成功后条件更新为 BCrypt；哈希样式字符串不能作为明文密码登录。

实际 Java 21 / Spring Security Crypto 6.5.7 合成向量验证：ASCII、中文与 emoji、内嵌 NUL、71 字节和恰好 72 字节可编码并验证；73 字节被拒绝。Rust 必须先检查 UTF-8 字节数不超过 72，再调用普通 `hash/verify`；`bcrypt 0.19.3` 的 `non_truncating_*` 会拒绝恰好 72 字节，不能直接替换。最短 4 字符规则按 Java UTF-16 长度兼容。原始合成向量保存在本地验收文件，后续由苏瑶加入版本化测试。

BCrypt 计算由持有并发许可的 `spawn_blocking` 完成，许可在阻塞任务真正退出前不得释放。改密、重置、删除与恢复在 PG 事务内推进 sessionVersion 和 rowVersion；改密保留当前会话，其他会话失效。PG 提交后 Redis 失败需要明确记录已提交的结果，不能自动重试整个数据库写操作。

管理员二次密码保持当前配置与 30 分钟时效。管理员身份与二次验证是两个独立判断；`/api/markers/all` 只要求管理员，其余现有审核与用户管理接口继续要求二次验证。

实际 Java HTTP 核验修正了缺管理员角色的错误入口：Spring Boot 会将默认 403 分派为含 timestamp、status、error、path 的 JSON，Rust 保持该形状。未认证入口仍为 401 `{message:"Spring Security Error"}`；二次密码和业务属主校验的中文文本错误分别保留。

## 注册唯一性：历史数据例外

温晓在隔离恢复库只读执行了聚合检查，发现非空用户名和规范化邮箱各有一组历史重复值，且包含未删除账号。未读取或公开这些值，未修改真实账号。

因此本轮不能直接给历史库加唯一索引，也不能自动删除、合并或改名。注册在专用 PG 事务级 advisory lock 下重新检查用户名与规范化邮箱，再插入；所有 Rust 注册入口使用同一个锁。密码哈希在持锁前计算，缩短临界区。真实 PG 并发注册测试证明不会产生新的重复记录。

这是一项明确的临时例外：数据库还没有用户名/邮箱唯一约束，其他绕过该用例的写入不受其保护。本次没有用户名/邮箱修改入口；阶段 4 切换认证写入时采用单后端，不能并行双写。发布前由 Nora 决定历史账号整理方式，再通过预检迁移加入唯一索引。不得把本轮实现描述为已经有数据库唯一约束兜底。

登录查询若匹配多个有效账号，返回普通的凭据失败，不能随意选择其中一个账号授权。现有账号、公共 ID 和关联业务数据全部保留。

## 浏览器与 App 请求

Web 当前使用 Axios 凭据请求，React Native 使用 `credentials: include` 和 `Accept-Language`。本轮不要求客户端改用 JWT 或增加新的登录步骤。

- 浏览器写请求若携带 Origin，只允许显式配置的来源；包括同源站点也应列入配置。Origin 为 null、非法或不匹配时拒绝。
- Origin 缺失时，拒绝明确的跨站 Fetch Metadata，存在 Referer 时验证其来源。原生 App 没有这些浏览器头的请求继续兼容。Cookie 保持 SameSite=Lax；JSON 接口拒绝表单内容类型。
- CORS 与写请求来源校验分别实施。允许跨域读取不等于允许跨站写入；上传入口也执行来源校验。
- 注册限流使用 Redis 原子 INCR + TTL。默认采用实际连接 IP；仅当连接来自显式配置的可信代理时读取 X-Forwarded-For，避免调用方自选限流身份。默认 5 次 / 600 秒；Redis 故障不无限放行。

## 验收

真实 PG/Redis 覆盖登录后并发读取不换 ID、退出与二次验证竞争、改密与旧验证竞争、删除/恢复/重置后的会话失效、角色变化、注册并发唯一性、限流故障、来源校验与 App 请求。使用 Java 生成的合成 BCrypt 向量验证 Rust，再验证 Rust 新哈希可以被 Java 回退版本识别。所有测试采用独立数据库和随机 Redis 前缀。

认证、用户、头像共 14 个现有路由，逐个验证响应形状；媒体处理与点位图片共享同一受限编解码与安全路径组件。阶段完成记录以实际命令和验收结果为准。
