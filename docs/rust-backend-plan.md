### 最新稳定版本优先，验证后锁定

上表已按 2026-09-14 的官方稳定版本核对并在本项目编译运行；完整来源、镜像 digest、验证结果与新增依赖见 [版本记录](rust-migration/versions.md)，阶段验收以 [执行记录](rust-migration/execution.md) 为准。后续升级仍核对发布说明、最低 Rust 版本与组件兼容要求。Rust 的 stable / beta / nightly 发布渠道有明确区分，本项目采用 stable。[Rust 发布渠道](https://doc.rust-lang.org/book/appendix-07-nightly-rust.html)。

通过编译、启动、关键接口、真实 PG / Redis、会话和恢复验证后，固定 `rust-toolchain.toml`，提交 `Cargo.lock`，让 SQLx CLI 与库版本匹配，只启用实际需要的 feature。数据库与容器运行组件记录精确版本；容器镜像同时记录 digest，确保构建和回退可复现。

运行中的服务不自动跟随 `latest` 标签变化。后续新稳定版按同样流程升级。若最新组合确实无法运行，苏瑶提交失败证据、替代方案及影响，由温晓评估最小必要的版本回退，并记录原因、影响范围和恢复升级的条件。

早期会话候选存在 core / Redis 适配器版本不匹配；实施已选择范围明确的 `SessionStore`，直接用 Fred 执行经过测试的原子操作。它只管理本项目的身份、版本与二次验证状态，普通请求不把整份会话回写。改密采用带期限与随机 nonce 的转换标记，使数据库提交和 Redis 版本更新之间的并发读取不会误删当前会话；细节及故障语义见 [认证设计](rust-migration/auth-design.md)。这仍是本轮兼容方案，后续认证重设计单独推进。

会话、缓存与限流统一使用 Fred，并分别封装职责及命名空间。Fred 支持异步连接、重连和 Lua 脚本。[Fred 官方文档](https://docs.rs/fred/latest/fred/)。

v0.1 调研时的 bcrypt 候选版本 0.19.3 已高于已知非 ASCII 哈希解析 panic 问题的修复版本 0.19.2。该记录用于说明已知兼容检查项，实施时重新选择最新稳定修复版本，最终以锁定依赖后的检查结果为准。[bcrypt 文档](https://docs.rs/bcrypt/latest/bcrypt/)、[对应 RustSec 公告](https://rustsec.org/advisories/RUSTSEC-2026-0199)。

### PostgreSQL 升级与数据延续

现有 PostgreSQL 17.8 是迁移来源，不是新后端的固定目标。2026-09-14 查询官方版本表时，最新稳定版为 PostgreSQL 18.6；后续实施若已有更新稳定版，则重新核对并优先采用。[PostgreSQL 官方版本表](https://www.postgresql.org/support/versioning/)。

数据库大版本升级安排独立演练：在隔离的新版本实例恢复现有数据，核对业务表、约束、序列、字符排序规则与 PostGIS 扩展兼容性，再验证 Java 回退版本和 Rust 新版本的查询与写入。现有数据规模下优先评估逻辑导出 / 恢复；正式步骤根据演练结果确定。PostgreSQL 大版本升级需要导出 / 恢复或 `pg_upgrade` 等升级流程。[PostgreSQL 升级说明](https://www.postgresql.org/docs/current/upgrading.html)。

数据库升级与应用切换分别设检查点。优先把“旧 Java 应用也能运行在升级后的数据库上”作为回退条件，这样应用回退可以继续保留新库中的写入。数据库版本回退另写包含切换后增量数据处理的方案，不能直接用旧数据目录替代已产生新写入的新库。

## 3. 架构：一个服务，按业务划分模块

部署流程：`Web / App → Nginx → Rust API → PostgreSQL / Redis / 上传目录`。

模块内请求流程：`HTTP handler → service → repository 中的 SQLx 查询 → PostgreSQL`。

| 边界 | 负责什么 | 约束 |
| --- | --- | --- |
| HTTP handler | 提取参数、调用用例、生成 HTTP 响应 | 保持薄层；业务授权不能只依赖路由是否可访问 |
| service | 权限、业务状态转换、事务编排、缓存失效 | 多步业务操作在此确定事务范围 |
| repository | SQL、行映射、受影响行数与数据库约束错误 | 接收调用方事务连接；查询中包含必要的数据范围条件 |
| model / policy | 业务类型、开放时间、可见性、译文有效性 | 能用纯函数表达的规则尽量不依赖网络或数据库 |
| infrastructure | 连接池、Redis、图片存储、配置、日志 | 不决定点位审核等产品规则 |

建议从单个 Rust package 开始，提供 `lib.rs` 供集成测试使用，`main.rs` 只负责装配和启动。各模块按需创建文件，不给每个 struct 配一套接口、实现类和通用 CRUD 基类。

Rust 后端目录为 `C:/Users/Nora/lycoris/backend-rust`，按以下责任边界逐步创建：

```text
backend-rust/
  Cargo.toml
  Cargo.lock
  rust-toolchain.toml
  src/
    main.rs
    lib.rs
    app.rs                 # Router 与 AppState 装配
    config.rs
    error.rs
    infrastructure/        # PostgreSQL、Redis、磁盘文件、观测
    middleware/            # 会话、身份、请求限制等
    modules/
      auth/                # 登录、注册、退出、管理员二次验证
      users/               # 用户资料、密码、删除恢复
      markers/             # 点位读写、搜索、附近、视口
        favorites/         # 收藏
        localization/      # 原文、译文、source hash
      moderation/          # 点位、编辑、图片提案审核
      media/               # 图片与头像上传、受控读取
  sql/                     # 按业务目录保存较长的命名查询
  migrations/              # 接管基线之后的版本化变更
  tests/                   # API、真实 PG/Redis、并发回归
```

`AppState` 保存可共享的池、配置和服务句柄。跨模块调用通过明确的服务或仓储函数完成。共享的数据库事务由最外层用例传入，避免一个审核操作意外使用多个独立连接提交。

## 4. SQLx 如何替代 JPA

SQLx 是 SQL 工具库。Rust struct 用于表示数据库行和业务数据，并不会自动产生 ORM 的脏检查、级联保存、关系加载或版本更新。

采用以下规则：

1. 固定查询优先使用 `query!`、`query_as!` 或 `query_file_as!`。长查询放入命名的 `.sql` 文件，方便审查和执行计划分析。
2. 搜索等动态查询用绑定参数构造。排序字段、方向和其他不能绑定为值的 SQL 片段来自固定白名单。
3. SQL 检查宏依赖开发数据库结构或离线元数据。提交 `.sqlx` 元数据；CI 在迁移后的测试 PostgreSQL 上执行 `cargo sqlx prepare --check`，普通离线构建使用 `SQLX_OFFLINE=true`。[检查宏及其边界](https://docs.rs/sqlx/latest/sqlx/macro.query.html)、[SQLx CLI](https://github.com/transact-rs/sqlx/blob/main/sqlx-cli/README.md)。
4. 编译检查能发现部分 SQL 与类型问题，无法证明权限、排序语义、性能或并发行为正确；动态查询还需要运行时验证。
5. 请求 DTO、数据库行和响应 DTO 分开，按需做最少映射，避免把密码哈希或内部字段带进响应。明确 PATCH 的缺失、null、空串在各字段上的既有含义。
6. 更新时保留现有乐观锁，例如 `UPDATE ... SET version = version + 1 WHERE id = $1 AND version = $2`。检查更新行数，区分缺失、无权访问和版本冲突，保持既有 404 / 403 / 409 行为。
7. 审核操作在同一 PG 事务中校验提案状态和基准版本、更新点位及译文、落审核结果。通过条件更新或必要的行锁，使同一提案只处理一次；冲突时全部回滚。
8. 注册唯一性、收藏唯一性、创建点位幂等性由数据库约束兜底。现存约束先盘点；任何新增约束先查历史冲突，作为单独迁移处理。
9. 原文编辑和译文编辑继续共用点位版本。读取时计算开放状态，不写回数据库或推进版本。

数据库 schema 接管以生产备份结构为依据，保留 ID、标识生成机制、外键、默认值、唯一约束和现有数据。空库初始化与已有数据库基线登记分别演练；已有库通过结构核对后才接入 SQLx 迁移记录，避免重复执行建表。新服务由发布步骤执行迁移，启动时只检查所需版本。

现有 Java 配置有 `ddl-auto: update`。迁移阶段应先在演练环境验证改为结构校验后能正常运行，避免 Java 与 SQL 迁移同时管理表结构。

## 5. 登录与权限

### 兼容阶段采用 Cookie + Redis Session，后续单独改造认证

Nora 已确认认证后续还要调整。下面描述的是兼容阶段的设计基线，Cookie 名称、认证凭据、会话库、登录流程、二次验证和密码策略都可以在认证专项中重新确定。实现前先整理该专项的目标和迁移边界，避免把过渡方案写成永久约束。

业务模块依赖经过校验的身份上下文及权限判断，HTTP Cookie、会话序列化和凭据验证集中在 auth / middleware 边界。这样后续认证变化主要落在入口和适配层；只有出现实际替换需求时才增加相应抽象。

Cookie 保存随机、不透明的会话 ID；登录身份保存在 Redis。保持现有 Cookie 的名称、作用域、HttpOnly、Secure、SameSite 与有效期配置语义，分别验证 Web 和移动端的 Cookie 保存及跨域行为。

会话只存必要身份信息，例如用户 ID、登录时的 `sessionVersion`、管理员二次验证状态及其有效期。请求中从 PostgreSQL 重查当前用户状态与角色。删除、恢复、改密等操作按现有规则推进 `sessionVersion`；旧会话不能恢复权限。

Axum 的 `CurrentUser`、`AdminUser` 等提取器负责身份入口，`can_view_marker` 等权限规则与服务层负责资源访问。管理员二次密码沿用当前机制和过期规则；它不是独立设备上的多因素认证。

浏览器写操作的 CSRF 策略需在认证阶段明确：按现有 Web / App 请求核对 Origin、允许的内容类型、Cookie 属性及是否需要令牌，再形成一致策略。CORS 白名单本身不能代替完整的 CSRF 防护。

### 新旧会话切换建议

Spring Session 默认使用 Java 序列化，现有代码未找到覆盖该序列化器的配置。共享 Redis 实例不意味着 Rust 能读取这些会话。[Spring Session 官方说明](https://docs.spring.io/spring-session/reference/configuration/redis.html)。

**建议正式切换时让用户重新登录一次**，Rust 使用新的 Redis 会话命名空间。这个用户体验取舍仍是建议，尚未执行。全站切换后可沿用原 Cookie 名称，由 Rust 忽略无法识别的旧 ID 并在重新登录时替换。

测试和并行验证使用独立 Cookie 名称与命名空间。正式切换时，登录、所有受保护 API 和受保护的图片读取必须进入同一套后端。回退时同样整体切回，并让用户重新登录，避免旧登录状态重新生效。

### 必须处理的并发与兼容问题

登录成功时只轮换一次会话 ID，普通请求不反复轮换。不要每个请求都把用户资料回写到整个会话对象。

tower-sessions 文档明确提醒并发读改写会话可能丢失更新。会话失效、二次验证和退出之间的并发需额外验证；通过原子状态更新、会话代次或删除后的防回写机制确保旧请求不能恢复失效会话。选择存储适配器时把这一能力列为验收项。[会话并发限制](https://docs.rs/tower-sessions/latest/tower_sessions/)。

现有密码采用 BCrypt，首版继续兼容其格式与工作因子。使用 Java 生成的测试哈希验证 Unicode、长密码和边界输入；不要因为 Rust 库的默认行为不同而使老密码失效。代码中已有历史明文密码登录后升级的兼容分支；先只统计历史格式，再保留受限升级路径，禁止把看似编码哈希的值当明文回退。密码格式变化单独安排，确保切换后的新增账号仍能被回退版本识别。

## 6. Redis、文件与失败处理

| 用途 | 设计 |
| --- | --- |
| 查询缓存 | 使用新命名空间和短 TTL；PG 是权威来源，Redis 不可用时回源；缓存命中后仍核对点位当前可见性 |
| 会话 | 使用独立前缀；Redis 不可用时受保护操作返回服务不可用，不凭旧资料放行 |
| 限流 | 原子设置计数与过期；故障时注册等受限操作默认返回暂时不可用，避免无限放行 |
| 数据写入与缓存 | 先提交 PG 事务再失效缓存；失效失败记录并依靠 TTL 收敛；不可因事后 Redis 失败误报数据库未提交 |
| 图片与头像 | 保留现有 URL 和挂载目录，受保护资源经过后端权限检查 |

图片处理沿用文件大小、尺寸、像素数量限制，检查真实可解码格式，重新编码后保存。BCrypt 和图片编解码属于 CPU 工作，放到受并发上限控制的阻塞任务中；异步请求超时不等于已经停止阻塞任务。[Tokio 对 spawn_blocking 的说明](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)。

PostgreSQL、Redis 和磁盘不共享一个事务。上传建议先完成临时文件处理，再原子移动到新名称，最后提交数据库引用；失败保留可清理的孤立文件，不产生指向未落盘文件的已提交记录。删除旧文件在事务提交后处理，清理必须重新确认无引用。首版保留现有目录结构和历史资源可读性。

日志包含请求 ID、路由、耗时、状态及受控的错误信息；密码、Cookie、会话 ID 和完整用户记录不进入日志。连接池上限、SQL 超时、图片处理并发和登录哈希并发均配置化，从保守值开始按测量调整。

## 7. 地理查询

第一阶段通过 SQLx 保留现有包围盒、Haversine、距离排序和参数边界，建立与 Java 的结果对比基线。

第二阶段单独采用 PostGIS：先核对经纬度有效性与坐标系，设计 `geography(Point,4326)` 和 GiST 索引，再使用 `ST_DWithin` 过滤附近点位。它的 geography 距离参数以米为单位，并能利用合适的空间索引。[PostGIS ST_DWithin](https://postgis.net/docs/ST_DWithin.html)。

届时单独确定球面或椭球距离的产品语义，同步 Web 与移动端的距离显示和半径过滤。新距离计算与当前球面公式可能在边界处有差异，不能直接把差异当作 Rust 实现错误。

首版附近列表规模限制和分页保持现有契约；后续分页应独立设计稳定排序及游标。扩展测试数据量后查看实际执行计划，再决定空间索引的具体形态。

| 2：认证与用户 | 认证专项设计、兼容阶段登录与会话、资料、密码、头像、用户管理 | 先明确当期采用的认证方案；现有账号可用，权限和登录体验通过验收；明确另行实施的认证改造任务 |
| 3：业务写入与审核 | 点位、收藏、译文、图片提案、管理员审核 | 幂等、重复审核、过期提案、并发修改及事务失败回滚均正确 |
| 4：发布演练 | 同负载测量、数据库升级与应用切换的独立步骤、回退步骤、媒体核对 | 功能回归通过，记录 RSS/CPU/P95/错误率/连接数；前后端完整流程、保留新增数据的应用回退和数据库升级演练通过 |
| 5：查询优化 | PostGIS 查询及对应索引 | 坐标与距离语义确认；执行计划和目标负载证明优化收益 |

Java 与 Rust 可并行运行进行比较，但写操作在隔离数据副本上验证。生产阶段先可选地试运行严格公开、无登录副作用的读路由；缓存需要兼顾 Java 写入后的可见性变化。身份相关路由最终整体切换，任何时候同一业务写请求只交给一个后端执行。

测试使用真实 PostgreSQL 与 Redis，覆盖查询、事务、约束、缓存和会话行为；纯规则使用单元测试。现有 Java 测试是迁移参考，需要转换为 Rust 或跨实现的 API 用例，不能以已有 Java 通过结果代替新后端验证。

重点回归：登录后同时请求多个接口；退出与正在进行的请求；权限变化；私有点位及图片；重复创建与收藏；两个管理员同时审核；原文与译文并发编辑；跨午夜开放时间；日期变更线、极区和半径边界；图片解码资源限制。

原文哈希需对 `[规范化语言, title 或空串, description 或空串]` 的紧凑 UTF-8 JSON 保持字节级一致，覆盖非 ASCII、换行与控制字符，使现有译文继续有效。

上线前补做当时的新备份，使用兼容的增量数据库变更及上传格式。回退恢复旧应用入口并保留切换后已写入的业务数据；不能把今天的旧备份直接覆盖回生产数据库。破坏性表结构清理放到回退窗口结束后。

内存降低幅度目前没有实测，不写成固定收益承诺。对比同一数据、同一机器资源和请求组合，分别测空闲、预热后的稳定负载、上传峰值与并发登录；同时记录 API 进程和整机资源。

## 9. 注释、简洁性与代码审美

注释与代码质量属于正式验收内容，苏瑶实现时遵循以下约定：

1. 注释解释“为什么”、必须成立的业务条件、失败语义和兼容原因。事务边界、乐观锁、权限、会话失效、距离单位、时间边界与源文本哈希需要清楚说明。
2. 模块和关键接口用 Rust 文档注释说明职责、输入限制与错误情况；普通代码依靠准确命名表达，不逐行复述。注释随实现一起更新，删除过时内容。
3. 标识符使用一致的英文业务名称，注释以团队能直接理解的中文为主；SQL 命名和布局保持一致。
4. 函数保持单一职责，按业务自然拆分，优先直接的数据流和明确的控制流。只有确有替换、复用或测试边界需要时才引入 trait 和泛型。
5. 不搭建通用 CRUD 框架，不增加只有一层转发作用的包装，不以复杂宏隐藏主要业务流程。结构体和 DTO 的拆分以责任边界为依据。
6. 错误使用清楚的类型和传播路径；请求输入、数据库和网络失败不靠 `unwrap` / `expect` 处理。业务源代码不引入 `unsafe`。
7. Rust 统一使用 rustfmt；SQL 采用一致缩进与命名风格。验收执行 `cargo fmt --check`、适用的 Clippy 检查和与任务相称的测试，同时人工检查可读性。
8. 以行为、边界和回归风险设计测试；不为增加数量而编写只复述实现的测试，不用无意义抽象换取可模拟性。
